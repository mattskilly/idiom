# Guided initialization

Produce a first honest `PRODUCT.md` and `DESIGN.md` for this repository in under
fifteen minutes: mining about five minutes, questions in at most two batches,
drafting and review the rest. Those two files are the human's contract — the
whole loop judges every finding against them — so they are the human's to
correct, and this procedure hands them back for correction rather than
declaring them done.

Two situations, one procedure: a repository that already has a design language
is mined and confirmed; a repository with none is helped to create one from the
interview and the captured references. Phase 1 decides which.

## Phase 0 — scaffold safely

Run `idiom init --yes` from the repository root. Always pass `--yes`: without it
the CLI opens an interactive stdin prompt a non-interactive shell cannot answer,
and `--yes` still never overwrites a differing file. Never run `idiom init`
without `--yes`.

Read the output. Every `Preserved existing <file>` line marks a **human-owned**
file — one that already exists and differs from the template. Record whether
`PRODUCT.md` and `DESIGN.md` are human-owned or pristine scaffold; that decides
the write rule in Phase 5.

## Phase 1 — mine the repository first, ask nothing yet

A bounded sweep of a few minutes at most; breadth beats depth. Look for:

- design tokens and theme stylesheets — CSS custom properties, a Tailwind theme
  config, a tokens package;
- global and component CSS, and the component directory or design package;
- written design or brand documentation — `README`, `DESIGN`, `STYLEGUIDE`,
  anything under `docs/`;
- the UI framework, the primary user-facing surfaces, and their states;
- the product's own copy — headings, empty states, error text — as evidence of
  voice.

Record every candidate claim with the path it came from; a claim with no path is
not yet a claim. Then state the outcome plainly: **an existing design language**,
or **none found**. That selects the branch in Phase 2.

If a token stylesheet is found, offer once to set `design.tokensFile` in
`.idiom/project.json` to that project-relative path — it is what makes the
`token-drift` check real — and edit it only on the human's yes.

## Phase 2 — ask only what the code cannot answer

At most six questions, in at most two batches, and each must be underivable from
the repository:

- who this surface is for, and what they must grasp in the first seconds;
- what observable outcome means it is working, and what must never be
  compromised;
- one to three links or screenshots of design they are **after**, each with one
  sentence of why;
- one to three they **dislike**, as the anti-pattern, each with why;
- a confirm-or-correct pass over the mined claims, presented as a short numbered
  list of statements each carrying its source path, which the human answers yes,
  no, or a correction per line.

Forbidden: asking anything the repository already answers (fonts, spacing scale,
component inventory); asking for adjectives instead of evidence; any taste quiz,
any scoring, any ranking of the human's answers; more than three liked or more
than three disliked items.

**When Phase 1 found none**, skip the confirm-or-correct pass, keep the same
questions, and treat the captured references plus the human's own words as the
only evidence — say so in the drafted files rather than implying repository
backing that does not exist.

### Include empty, error and loading cases

Ask which surfaces have empty, error and loading states and how to force each
with fixture data or query flags. Declare a state per case, for example:
```json
[
  { "id": "empty", "description": "No leads yet", "url": "/leads?fixture=empty", "expect": {} },
  { "id": "error", "description": "Request failed", "url": "/leads?fixture=error", "expect": { "textPresent": ["Could not load leads"] } },
  { "id": "loading", "description": "Generating", "url": "/leads?fixture=loading&delay=2000", "steps": [{ "action": "click", "selector": "#generate", "longRunning": true }], "expect": {} }
]
```
The app implements these flags or supplies fixture data through flow `setup`.
Delay loading responses; mark slow web mutation steps `longRunning`.
Configure canvases in project `checks`, for example `"emptyState": { "regions": [{ "selector": "main.canvas", "items": ".block" }] }`.
Both selectors are required. Recapture after changing regions or ignores.

## Phase 3 — capture the references

First read `viewports[].name` from `.idiom/project.json` and pick one; the widest
is the sensible default. `--viewport` is resolved against that list, and an
unmatched name fails the capture with `unknown project viewport "…"`, so never
assume the template's default name — a repository may have renamed its viewports.

Then, for every offered link:

`idiom reference add <slug> --url <url> --viewport <viewport> --note "<the human's reason, verbatim>"`

and the same with `--anti` for the disliked ones. For every offered screenshot or
local image:

`idiom reference add <slug> --file <path> --note "<reason>"`

`--viewport` is required with `--url` and rejected with `--file`. The slug is a
lowercase hyphenated slug drawn from the human's own words. The note is required
and is the human's reason — never invent the note. A capture failure (missing
Chromium, a non-2xx navigation, an image over the model transport limit) is
reported with the CLI's own error and offered the `--file` fallback, never
silently retried. Never delete a loose legacy reference directory.

Confirm with `idiom reference list`, and cite references in `DESIGN.md` by the
labels it prints.

## Phase 4 — draft both files

Keep the templates' exact section headings. `PRODUCT.md`: Target user, Job to be
done, Flow objective, What must be obvious, Success criteria, Hard constraints.
`DESIGN.md`: Visual character, Typography and hierarchy, Density and layout,
Components and patterns, Interaction conventions, References, Anti-references,
We do, We do not.

Every claim carries its source inline — a repository path, a managed reference
name, or "from the interview". Anything with none of those is written as an
explicit unknown, never guessed. `We do` and `We do not` are the enforceable
lines; they come from the human's confirmed answers and from the anti-references.

## Phase 5 — hand it back

Present both drafts in full and say plainly that they are the human's files to
correct. Invite amendments and apply them before writing.

Write rule: a pristine-scaffold file may be written once the human approves the
draft; a **human-owned** file — one Phase 0 saw as `Preserved existing` — is
never overwritten without explicit approval. Show what would change, offer a
section-by-section amendment, and write only on explicit approval of the result.

Close with `idiom reference list`: it parses `.idiom/project.json`, so it is the
configuration check a freshly initialized project can actually pass, and it
prints the labels to cite. Run `idiom validate` **only if** `.idiom/flows/`
already holds a `*.json` manifest — guided init authors none, and without one the
command exits 1 with `.idiom/flows: no flow manifests found`, which is the
expected state of a freshly initialized project, so do not run it there and do
not report it as a failure.

Then report both file paths and the captured reference labels, and name the next
step: author a flow manifest, then `/idiom <flow>`.

Never edit product code, generate tokens or components, or start Autobuild or
any other dispatcher.
