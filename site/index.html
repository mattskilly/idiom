Design QA

Heading · Archivo 700

Your agent built it. Idiom checks it the way a designer would.

One command captures every state of your app and what happens between them, finds the defects people notice, and says how to fix each one.

# example output
$ idiom check studio

2. [major] unexplained-control — editor/desktop — summary
   Problem: a control labelled only "?" with nothing saying what it does.
   Done when: a tooltip on hover and focus names what it does.

$ idiom check studio --baseline main

How it works

It looks at the app your users see, not just the code.

  1. Learn

    Idiom reads your design tokens and DESIGN.md, or idiom init writes them with you.

  2. Render

    It opens your running app in a real browser and captures every state you care about (empty, error, signed in) at each viewport, in light and dark. It clicks controls to see whether they do anything and records what happens during every load and click: what moved, what appeared and what animated. It replays requests as a slow network would to see what a user waits through, and never sends requests that change your data.

  3. Critique

    More than 60 measured checks, plus your intended design if you have one. Top issues come first, ranked by how noticeable each problem is and how prominent the element is. Symptoms that share one cause become one issue. Each finding says whether it was measured, observed in an interaction or judged by a model, and gives a check that proves the fix. It waits for entrance animations to finish, then judges only what is on screen: anything in a closed menu, a collapsed section or still invisible is skipped and counted, not measured.

  4. Repair

    Every finding carries the element, the measurement, a cropped screenshot and a fix your agent can apply, or idiom fix hands them to it.

  5. Verify

    Idiom renders the same states again and confirms the problem is gone. The exit code is the verdict, so it works in CI.

  6. Remember

    Your accept and reject decisions live in the repo, so a settled finding doesn't come back.

What it catches

The things a person notices in the first minute.

Accessibility linters and screenshot diffs pass all of these. Each card is a real finding on one of Idiom's example screens: a crop of the problem, what is wrong, and when it counts as fixed.

major dead-control

A button that does nothing

“Name this version” is enabled, but clicking it changed nothing: no DOM change, focus move, navigation, dialog or network request.

Done when Clicking it shows a result, or it is disabled with a reason, or it is removed.

major unexplained-control

An icon nobody can read

A control labelled only “?” with no tooltip and no name that says what it does.

Done when A tooltip on hover and focus names what it does.

minor text-centering

A label sitting low

“Button” sits 2px below the vertical centre of its 28px chip.

Done when The label sits within 1.5px of centre.

major adjacent-gap

Controls touching

The message field and Send sit 0px apart. Neighbouring controls need at least 3px.

Done when The two controls have room between them, focus ring included.

minor duplicate-entry

Two ways to do one thing

Three controls open the same Page settings panel: the page-name gear, the tool-row gear and the Project menu.

Done when One entry point, or the others recorded as deliberate.

major copy-lint

Code names in the copy

“On primary on primary” repeats itself.

Done when A label that reads naturally, such as “Text on primary”.

It also catches what a screenshot can't show, because it happens between states: content that jumps when you click, a button that shows nothing while its request is pending or can be pressed twice, an action that fails silently or can't be retried when its request fails, and panels or content that snap into place with no transition.

And it checks the basics every product should get right:

  • low contrast
  • broken links
  • broken or stretched images
  • fonts that fail to load
  • missing focus styles
  • lines too long to read
  • orphaned words
  • layout shift on load
  • targets too small to tap
  • uneven spacing
  • clipped and overlapping text
  • error text left on screen
  • sizes off your design system

Your design

Hold the build to the design you meant.

Point Idiom at your intended design and it reports where the build drifts: spacing, size, colour and missing or extra elements, measured on the real render. When designs disagree with each other, it asks you to choose once and remembers. When the same off-scale value keeps turning up in one place, it asks once whether your design system is missing a step, instead of filing every occurrence.

With your agent

Built for the loop your agent already runs.

  1. 1

    Check. After a UI change, the agent runs idiom check <flow> and gets every finding in fix order, with a crop of each. idiom check --changed checks only the states its change touches. In Claude Code, Idiom's plugin reminds the agent when it edits UI and before it stops.

  2. 2

    Fix. It fixes the blocking ones and runs the check again until it is clean. Findings it disagrees with go to you, never quietly away.

  3. 3

    Gate. In CI or autobuild, idiom check <flow> --baseline <run> --fail-on major fails only on new problems. Model judgements gate only if you opt in with --fail-on-judged. On a pull request, the GitHub Action posts one comment that sorts new findings into Blocks merge, Should fix and Opportunities, each with its fix and how to confirm it.

Works with Claude Code, Codex, Cursor and autobuild, from the CLI or as MCP tools for every step of the loop: claude mcp add idiom -- npx -y @mattskilly/idiom mcp, or as a portable agent skill: npx skills add mattskilly/idiom --skill idiom. Over MCP, a problem that happens between states comes with a filmstrip of what the user saw. After an autonomous build, idiom sweep --all reviews every flow and ranks the cleanup. Your decisions are stored in the repo, so the same finding is not raised twice.
